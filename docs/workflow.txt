 1. HOW TO RUN
--------------------------------------------------------------------------------
Prerequisite: Node.js 20+ (installed: v22.14.0)

  npm install        (first time only; also builds the shared package)
  npm run dev        starts 3 things together:
                       [db]  local MongoDB replica set on 127.0.0.1:27017
                       [api] Express backend on http://localhost:5000
                       [web] Next.js frontend on http://localhost:3000
  npm run seed       (in a 2nd terminal, while dev is running)
                     resets demo data: accounts, demo borrowers/loans, audit log,
                     reminders
  npm test           runs all automated tests (10 shared + 29 backend)

Open http://localhost:3000. The login page has one-click demo account buttons.

Other scripts:
  npm run db          start only the local database
  npm run dev:atlas   start api + web without the local DB (when using Atlas)
  npm run typecheck   TypeScript check for all 3 packages
  npm run build       production build

Settings files (NOT committed to git, contain the secret key):
  backend/.env          PORT, MONGODB_URI, JWT_SECRET, JWT_EXPIRES_IN,
                        CLIENT_ORIGIN, UPLOAD_DIR, REMINDER_INTERVAL_MINUTES
  frontend/.env.local   BACKEND_URL, JWT_SECRET (must match the backend's)
  Templates: backend/.env.example, frontend/.env.example

Database data lives on disk in backend/.mongo-data, so it survives restarts.
Uploaded files live in backend/uploads.
To use MongoDB Atlas instead: put the Atlas URI in backend/.env and run
"npm run dev:atlas".

 5. DATABASE DESIGN (MongoDB collections)
--------------------------------------------------------------------------------
All money is stored as INTEGER PAISE (no floating-point errors). The API sends
and receives rupees; conversion happens in one place (mappers.ts / zod).

Relationships:
  User 1 --- 0..1 BorrowerProfile
  User 1 --- N    Document          (uploaded salary slips)
  User 1 --- N    Loan              (as borrower)
  User 1 --- N    Loan              (as current assignee / executive)
  Loan 1 --- N    Payment
  Loan / User 1 --- N AuditLog      (actor, subject borrower, loan)
  User 1 --- N    Notification

users
  name, email (unique, lowercase), passwordHash (select:false, never returned),
  role (ADMIN|SALES|SANCTION|DISBURSEMENT|COLLECTION|BORROWER), isActive,
  createdAt, updatedAt
  Indexes: {email} unique, {role, createdAt}

borrowerprofiles  (1:1 with a borrower, kept apart so auth lookups stay small)
  user (unique), fullName, pan (uppercase), dob, monthlySalary (paise),
  employmentMode, bre {passed, failures[{rule,message}], checkedAt},
  salarySlip (ref Document)
  Failed BRE results are saved too, so Sales can see why a lead dropped off.
  Indexes: {user} unique,
           {pan} unique PARTIAL where bre.passed=true (one PAN = one eligible
           borrower)

documents
  owner, kind (SALARY_SLIP), originalName, storedName (random UUID on disk),
  mimeType, size
  Indexes: {owner}, {storedName} unique

loans
  borrower, applicant (SNAPSHOT of profile at apply time), salarySlip,
  assignee (executive owning the current stage), principal, interestRate (12),
  tenureDays, simpleInterest, totalRepayment, amountPaid (all paise),
  status (APPLIED|SANCTIONED|REJECTED|DISBURSED|CLOSED), isOpen,
  rejectionReason, sanctionedBy/At, rejectedBy/At, disbursedBy/At,
  dueDate (set at disbursement), closedAt,
  consent {termsVersion, acceptedAt, ipAddress},
  statusHistory [{from, to, by, at, note}]  (embedded, at most 4 entries)
  Indexes: {status, createdAt}  -> every ops queue
           {borrower, createdAt} -> "my loans" + Sales lookup
           {borrower} unique PARTIAL where isOpen=true
                                 -> DB guarantees ONE open loan per borrower
           {assignee, status}    -> "Assigned to me" + least-loaded assignment
           {status, dueDate}     -> reminder job + Overdue tab

payments  (own collection: unbounded, needs a global unique UTR)
  loan, utr (unique, uppercase), amount (paise), paymentDate, recordedBy
  Indexes: {utr} unique, {loan, paymentDate}

auditlogs  (APPEND-ONLY: update/delete through the model throws an error)
  actor (null = system), actorRole, action, loan, subjectUser, details
  (snapshot incl. names), ipAddress, createdAt
  Actions: USER_REGISTERED, PROFILE_SUBMITTED, SLIP_UPLOADED, LOAN_APPLIED,
           LOAN_ASSIGNED, DOCUMENT_VIEWED, LOAN_SANCTIONED, LOAN_REJECTED,
           LOAN_DISBURSED, PAYMENT_RECORDED, LOAN_CLOSED
  Indexes: {actor, createdAt}, {subjectUser, createdAt}, {loan, createdAt}

notifications
  user, type, title, message, loan, readAt, dedupeKey, createdAt
  Types: DUE_REMINDER, OVERDUE, OVERDUE_ALERT, LOAN_SANCTIONED, LOAN_REJECTED,
         LOAN_DISBURSED, PAYMENT_RECEIVED, LOAN_CLOSED, LOAN_ASSIGNED
  Indexes: {user, createdAt}, {user, readAt},
           {dedupeKey} unique PARTIAL (reminders never sent twice)

Design decisions (embed vs reference):
  - statusHistory EMBEDDED: small, always read with the loan
  - applicant SNAPSHOT embedded: legal record of what was approved, and the
    Sanction queue needs no join
  - payments REFERENCED: unbounded, need their own unique UTR index
  - amountPaid DENORMALIZED on loan: outstanding balance is read instantly;
    kept correct by updating it in the same transaction as the payment insert
  - Queries use .lean() + projections, pagination (max 50 per page),
    parallel count, aggregation pipelines ($lookup/$facet) for leads,
    users and stats

 6. BUSINESS RULES
--------------------------------------------------------------------------------
BRE (eligibility), in shared/bre.ts. The SERVER decides; the client runs the
same function for a live checklist:
  Age        23 to 50 inclusive (birthday-accurate)
  Salary     at least Rs 25,000 per month
  PAN        ^[A-Z]{3}[ABCFGHLJPT][A-Z][0-9]{4}[A-Z]$  (4th char = holder type)
  Employment not UNEMPLOYED
  -> returns ALL failed rules at once (HTTP 422), re-checked again at apply time

Loan math (shared/loanMath.ts, integer paise):
  SI = (P x 12 x T) / (365 x 100), T = days; Total = P + SI
  Example: Rs 1,00,000 for 180 days -> SI Rs 5,917.81 -> Total Rs 1,05,917.81
  Limits: amount Rs 50,000 to 5,00,000; tenure 30 to 365 days
  The server recalculates on apply and ignores any totals sent by the client.

Dates: all business dates use India time (IST), so "today" is correct even at
midnight-5:30 AM on a UTC server (a real bug found and fixed).

Loan state machine (loanStateMachine.ts):
  APPLIED --approve (SANCTION/ADMIN)--> SANCTIONED --disburse (DISBURSEMENT/ADMIN)
     |                                                        |
     +--reject + reason (SANCTION/ADMIN)--> REJECTED          v
                                  DISBURSED --fully repaid (SYSTEM)--> CLOSED
  - Every change is conditional on the current status, so if two people click at
    once, one wins and the other gets 409
  - Any other transition gets 409 INVALID_TRANSITION
  - One open loan per borrower; they can re-apply after CLOSED or REJECTED

Payments (Collection):
  - Loan must be DISBURSED; amount > 0, max 2 decimals, <= outstanding
    (no overpayment)
  - Payment date not in the future and not before disbursement
  - UTR: 6-30 letters/numbers, uppercase, globally unique (409 on duplicate)
  - ONE TRANSACTION: insert payment + increase amountPaid + audit +
    notification + auto-close when outstanding = 0

Assignment:
  - Every loan has an assignee for its current stage, chosen automatically as
    the active executive of that role with the FEWEST open loans
  - Re-assigned automatically on each stage change; ADMIN can re-assign manually
  - Any executive of the role may still act; the audit log records
    "assignedTo" and whether the assignee did it

 7. SECURITY & ROLE-BASED ACCESS (RBAC)
--------------------------------------------------------------------------------
  - Passwords: bcrypt (10 rounds); login compares against a dummy hash for
    unknown emails, so response time doesn't reveal which emails exist
  - JWT in an httpOnly, SameSite=Lax cookie (JavaScript can't read it)
  - Next.js proxies /api/* to Express: same origin, no CORS problems
  - authenticate: 401 if not logged in; reloads the user from the DB on every
    request (so deactivation or a role change applies immediately)
  - authorize(...roles): 403 if wrong role; ADMIN always allowed
  - borrowerOnly: borrower portal is BORROWER-only (admin too gets 403)
  - Public sign-up always creates BORROWER (sending role:ADMIN is ignored)
  - Frontend middleware.ts redirects users away from pages they can't use
    (with a "no access" message). The API enforces the same rules, so hiding
    menus is not the only protection.
  - Each module only sees its own statuses (e.g. Sanction can't read a
    Collection loan)
  - Uploads: PDF/JPG/PNG only, max 5 MB (413), file type checked by its first
    bytes, not just the name (415), random stored name, never served
    publicly; only owner, SANCTION and ADMIN can open them
  - helmet security headers, rate limit on login/register, 100kb JSON limit,
    regex-escaped search, logs hide passwords and cookies

HTTP status codes used:
  200/201 ok, 400 validation, 401 not logged in, 403 wrong role, 404 not found,
  409 conflict (duplicate email/UTR/PAN, open loan exists, invalid transition),
  413 file too big, 415 wrong file type, 422 BRE rejected,
  503 database unavailable, 500 unexpected

 8. COMPLIANCE FEATURES
--------------------------------------------------------------------------------

  - Every document view by staff is logged ("who reviewed the documents")
  - Separation of duties: the sanctioner can't disburse, the disburser can't
    approve
  - Action + audit entry + notification saved in ONE transaction (no approval
    without a record)

 9. NOTIFICATIONS, DUE DATES & OVERDUE
--------------------------------------------------------------------------------
Repayment model: ONE repayment of the full amount, due on the due date
(no monthly EMIs in this assignment). dueDate = disbursement date + tenure
(IST), stored on the loan.

In-app notifications (bell icon with unread count, for borrowers AND staff):
  Borrower: approved / rejected (with reason) / money sent (with due date) /
            payment received / loan closed / due tomorrow / overdue
  Staff   : new loan assigned to you / re-assigned / borrower overdue alert

Reminder job (notifications/reminderJob.ts):
  - Runs when the server starts, then every 60 minutes
    (REMINDER_INTERVAL_MINUTES)
  - Admin button "Run reminder check now" on Overview (POST
    /api/admin/jobs/reminders)
  - ~24h before: "Payment due tomorrow" to the borrower
  - Overdue: reminder to the borrower on day 1, 3, 7, then every 7 days;
    the assigned collection executive gets an alert on the same days
  - Unique key per loan per day, so running it many times never sends
    duplicates
  - Overdue loans: red "Overdue - Nd" badge, Collection "Overdue" tab (most
    overdue first), red banner for the borrower, "Overdue loans" count on admin
    Overview
  - Not built on purpose: late fees / penal interest (would change the graded
    loan math); email/SMS (records are ready for it)
